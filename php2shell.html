PHP2Shell
The Bug That Runs Before Your Code

01 What Happened

On 21 October 2026 the PHP project shipped emergency releases for two vulnerabilities collectively named PHP2Shell: CVE-2026-109618 and CVE-2026-109619. Both are rated 9.2 on CVSS v4.0. Both sit in the PHP engine itself rather than in any library, framework or application.

The practical consequence is that an unauthenticated HTTP request can reach the flawed code. PHP confirmed remote code execution on Apache with mod_php, where the request is handled in-process. The second flaw can also leak process memory even where an attacker fails to achieve execution.

Scope: this is not a plugin, a CMS or a framework issue. If a host runs an affected PHP build and serves requests, it is in scope — NGINX with PHP-FPM, Apache with mod_php, containers, CI runners, and the forgotten internal tool nobody has redeployed since 2023.

03 The Two Bugs

CVE-2026-109618 — corruption on the out-of-memory path

This one is a cleanup failure. While PHP is still assembling the incoming request data, it exhausts its configured memory limit. The error-handling routine that runs next treats the half-constructed structure as if it were complete and valid, and operates on it.

The trigger demonstrated in testing is mundane: a single unauthenticated POST carrying one enormous form field name — around 3.5 MB. No credentials, no session, no application interaction. The failure occurs during request initialisation.

CVE-2026-109619 — stale state reused across requests

The second is a use-after-free. State belonging to one request survives past the point its memory is released. A subsequent request handled by the same worker process then reuses that freed memory, and an attacker who can influence what lands there can control the contents.

This path depends on session.upload_progress.enabled, which is on by default. One sub-path involving fatal error backtraces applies only to PHP 8.5. Where execution is not achieved, the flaw can still disclose process memory — which on a busy application server may include credentials and session material.

The shared property: neither bug requires authentication, a specific framework, or any particular application feature. They live in the machinery that turns bytes on a socket into a request PHP can act on — machinery every PHP application uses.

04 Why Hardening Fails Here

The 9.2 rating is the least interesting number in this advisory. What makes PHP2Shell worth studying is position in the stack.

Most of what we build to defend an application runs inside the application: authentication middleware, session validation, CSRF tokens, input sanitisation, role checks, rate limiting on sensitive routes. All of it is reached only after PHP has parsed the request and handed control to your code.

These flaws fire before that handoff. The controls are not bypassed or weakened in any clever way — they are simply never reached. A perfectly audited application with exemplary input validation is in exactly the same position as an abandoned one.

This inverts normal triage. The usual first question — are we actually using the vulnerable feature? — has no useful answer. If the host parses HTTP requests with an affected PHP build, it is exposed. That makes asset inventory, not patch analysis, the critical capability.

05 The Disclosure Broke Down

Coordinated disclosure exists to give defenders a patch before attackers get a target. Here that sequencing failed twice.

An exploitation attempt was logged on 17 October, four days before any fix existed publicly. Then on 20 October, vulnerability details leaked ahead of the scheduled release. By the time fixed builds appeared the following afternoon, the usual grace period between public knowledge and available patch had collapsed to roughly nothing.

Worth internalising: embargo is a courtesy between researchers and vendors, not a security control. Any plan that assumes a quiet window between disclosure and exploitation is planning around a convention that has now visibly failed. Patch velocity is the control; the embargo was never load-bearing.

06 Detection

Useful indicators exist, but they come with an important caveat covered below.

SignalWhat it means
Very large request bodiesRelevant to CVE-2026-109618. Bodies are frequently not logged, so filter on request size at the proxy or WAF rather than content.
Unknown on line 0Memory-exhaustion errors in PHP logs consistent with the out-of-memory path being hit.
AH00052 in Apache logsA child process crashed. Indicates the engine fell over while handling a request.
Shell parented to a web workerStrong post-exploitation signal. A shell whose parent is apache2, httpd, php-fpm or php-cgi has no legitimate explanation.
New files in upload / cache / tmpWebshell placement. Worth baselining these directories regardless of this CVE.
CVE-2026-109619No published log signature. Absence of evidence carries very little weight here.
The analyst’s caveat: crash logs measure attempts, not compromises. A spike in AH00052 tells you someone tried something clumsy. It does not tell you they succeeded. Equally, a clean exploit may leave neither a crash nor a memory error — so a quiet log is not a clean bill of health. Treat these as triage leads, not verdicts.

07 Remediation

Upgrade the runtime. Application-level changes do not help, because PHP handles the request first.

BranchFixed release
PHP 8.5.x8.5.12
PHP 8.4.x8.4.27
PHP 8.3.x8.3.36
PHP 8.2.x8.2.35 — note this branch reaches end of life on 31 December 2026
PHP 8.6 RC8.6.0RC4. RC3 does not carry the fix.
PHP 8.1 and olderNo official release. Minimal source backports were published for 7.4, 8.0 and 8.1, and some distributions ship patched packages.
  • Check the package, not the banner. Distributions such as Ubuntu and Red Hat backport fixes without changing the upstream version string, so php -v can look unpatched when it is fine — and occasionally the reverse. Compare package versions.
  • Rebuild images with docker build --pull. Anything pinned to a specific patch tag needs the tag updated first, or you will faithfully rebuild the vulnerable version.
  • Restart every PHP worker after upgrading or changing configuration. Long-lived workers keep running old code.
  • Partial mitigations where patching must wait: session.upload_progress.enabled=0; on PHP 8.5 also fatal_error_backtraces=0; and pm.max_requests=1 under PHP-FPM, which breaks the same-worker requirement at a performance cost. These narrow the window. They do not close it.
  • If you find signs of compromise, do not patch first. Isolate the host, capture memory, disk and logs, then rotate every credential the PHP process could read. Patching destroys the volatile evidence that tells you what happened.

08 The AI Angle

The first of these flaws was found during an AI-assisted audit of the PHP source. That detail has been widely reported, and it deserves more thought than the headline it usually gets.

PHP is roughly thirty years old. Its request-handling path is among the most heavily trafficked code on the public internet, read by an enormous number of competent engineers over decades. A memory-safety bug reachable by an unauthenticated POST survived all of that, and then two independent parties found it within a month of each other once this class of tooling was pointed at it.

The honest reading is not that AI is magic, nor that human review failed. It is that a cheap new way of searching old code has appeared, and the cost of finding this class of bug has dropped sharply. That cuts both ways: the same economics apply to anyone auditing your dependencies, and to anyone auditing them for less friendly reasons.

What I take from it: expect more of these — long-dormant memory-safety issues in mature, widely-deployed C codebases, surfacing faster than the old disclosure rhythms were built to handle. The defensive answer is unglamorous and entirely within reach: know every host you own, know what runtime it runs, and be able to patch it quickly. PHP2Shell rewards inventory and patch velocity. Nothing else helped.
